## Durable session API

The additive `20261002020000_durable_learning_sessions.sql` migration stores versioned SessionPlan snapshots in `learning_sessions` and exact request receipts in `learning_session_receipts`. RLS allows learners to read only their own sessions; browser writes and receipt reads are denied. Service-only operations verify ownership, source eligibility, immutable session mode/budget, and optimistic session revisions. Composite ownership FKs constrain sessions and receipts. Advisory locks serialize same-session creation/actions and same-request reuse; row locks and CAS serialize revisions. Source rows used by a committed recommendation are locked against concurrent deletion/content/status changes until transaction end. Failure rolls back both session and receipt.

`STUDIGO_DURABLE_SESSIONS=1` enables `/api/v1/learning/sessions`; absent/disabled returns 404. Apply the reviewed additive migration before enabling it. Keep existing adaptive/Coach flags independently controllable. Disabling the session flag preserves persisted history and existing product routes. No hosted migration has been applied here.

GET requires `roomId` and `sessionId` UUIDs and resumes the stored snapshot with database `now`. This is a read-only resume, not an implicit fresh recommendation. POST requires `roomId`, `sessionId`, `requestId`, `expectedRevision`, `action`, `mode`, `minutes` and optional `selectedTopicId`. Actions are `start`, `recommend`, `select`, `end`; budgets are 15/30/60/120 minutes and modes study/cram. `start` uses expected revision zero and starts at revision zero. Subsequent accepted actions increment revision. `select` with null clears explicit choice and restores automatic scheduling. `end` closes this session without claiming assessed success or creating evidence, including after sources disappear.

Auth accepts existing Supabase validated bearer or cookie identity; malformed bearer cannot fall back to cookies. Request parsing rejects unknown fields and exceeds at most 4096 bytes, including chunked/Unicode bodies. Clients cannot supply identity, learner state/mastery, timestamps, elapsed time, pending topic, or plan output. Server elapsed time uses DB `now` and stored DB start. Canonical event replay supplies concept evidence. Explicit selections are retained until cleared; unsupported/deleted explicit choices require reselection. Source-aware scheduling requires ready owned documents with actual non-whitespace chunks; metadata/chunk_count alone is insufficient. Caller RPC `read_session_source_scope` returns IDs only, without private chunk text.

A reused request ID with identical client intent returns the original immutable committed snapshot, even after evidence/sources change, and creates no second action. Reused IDs with different scope/action/revision/choices conflict. Distinct IDs with stale revisions conflict (HTTP 409). An exact retry can return an older revision; resume GET obtains the latest snapshot. GET/POST successful responses use private no-store headers.
